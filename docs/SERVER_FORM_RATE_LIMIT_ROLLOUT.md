# הגבלת קצב לטפסי האתר — הכנה להפעלה

עודכן: 28.10.2026. **הקוד מוכן לבדיקה; לא הופעל באתר החי ולא הוחלה מיגרציית הקצב.**

## ההתנהגות שהוכנה

שני הטפסים יכולים לשלוח אל `/api/forms` במקום ישירות ל-Supabase. המונה נשמר במסד המשותף: המתנה של 30 שניות, ועד חמש שליחות שאושרו בעשר הדקות האחרונות, לכל טופס ולכל מקור רשת. משתמשים מאותה כתובת IP חולקים מכסה; זו הגנה בסיסית מפני שימוש יתר ולא זיהוי של אדם או הגנה מלאה מרשת בוטים מבוזרת.

במסד ננעלת שורת מכסה אחת, מסוננים הזמנים שיצאו מהחלון, ונכתבים המכסה והתוכן באותה טרנזקציה. אם הכנסת התוכן נכשלת, גם צריכת המכסה מבוטלת. כשל במסד מחזיר 503; חריגה מהמכסה מחזירה 429 ו-Retry-After. אין חזרה אוטומטית לכתיבה ישירה במצב שרת.

הנתיב בודק מקור בקשה, JSON, גוף עד 8KB, שדות מורשים, אורכי טקסט ודירוג. כתובת המקור נקראת מכותרת Vercel מהימנה רק בסביבת Vercel. בפיתוח מקומי יש מפתח משותף אחד ל-localhost. בסביבת שרת אחרת הנתיב יסרב לפעול עד להתאמת מקור IP מהימן.

לא נשמרת כתובת IP גלויה במונה: נשמר HMAC של כתובת המקור וסוג הטופס. זהו מזהה פסאודונימי, לא טענה לאנונימיות מוחלטת. מפתח HMAC שונה לכל טופס; אין לקשר את המזהה לשמות או לתוכן. פקיעת תוקף לאחר יום משמשת לניקוי מדורג של עד 100 שורות בפנייה. בהיעדר תעבורה השורות עשויות להישאר יותר מיום: כדי להתחייב לתקופת שמירה יש להוסיף ניקוי מתוזמן ולבדוק את הריצה שלו. הצעת נוסח לעדכון הפרטיות מופיעה בהמשך.

## הגדרות נדרשות — עדיין לא הוגדרו

| משתנה | תפקיד |
| --- | --- |
| `NEXT_PUBLIC_FORM_SUBMISSION_MODE=server` | בחירת מסלול השרת בבניית האתר ובשרת. בלי הערך הזה נשמר המסלול הקיים וה-API החדש מחזיר 404. מחייב build חדש. |
| `SUPABASE_SECRET_KEY` | מפתח שרת מאובטח ל-Supabase, בעל הרשאות service_role. לא NEXT_PUBLIC ולא בקוד הדפדפן. |
| `FORMS_RATE_LIMIT_SECRET` | סוד אקראי קריפטוגרפי של לפחות 32 תווים לחישוב HMAC. לא לשתף בצ׳אט ולא להכניס ל-Git. |
| `FORMS_ALLOWED_ORIGINS` | רשימת מקורות מדויקים מופרדים בפסיקים, כולל הפרוטוקול והדומיינים שבהם האתר פועל. ללא wildcard. |
| `NEXT_PUBLIC_SUPABASE_URL` | כתובת הפרויקט הקיימת. |

לא נשמרו מפתחות חדשים ולא שונו משתני הסביבה הקיימים. אין תלות חדשה בזמן ריצה ואין שירות חיצוני נוסף שנבחר בתשלום. ניצול המשאבים כפוף למכסת התשתית הקיימת.

## סדר הפעלה — דורש אישור נפרד

1. להכין סביבת בדיקה מבודדת, ולהחיל בה את מגבלות התוכן שכבר קיימות במסד הפעיל ואת `proposed-server-form-ratelimit.sql`.
2. להגדיר את המפתחות בממשק משתני הסביבה המאובטח, ולהכין פריסת Preview עם מצב server. אין להדפיס את ערכי הסודות או לשלוח אותם לצ׳אט.
3. לבדוק שליחה תקינה, 429, המתנה, איפוס חלון, תקלה במסד, ופניות מקבילות משני חיבורי PostgreSQL נפרדים. יש לכלול פניות ראשונות מקבילות ומיצוי מכסה מקביל. PGlite אינו מחליף את הבדיקה הזאת.
4. לאחר אישור לפריסה: להחיל את מיגרציית השרת במסד הפעיל, בלי לבטל עדיין את המסלול הישן. לבצע פריסה מתואמת של האתר עם מצב server והמפתחות, ולעדכן את תיאור אבטחת הטפסים בפרטיות.
5. לוודא שהאתר החדש שולח דרך API ורק אז להחיל `proposed-disable-direct-form-inserts.sql`. גם INSERT בעמודות בלבד מוסר, ולא רק ההרשאה הכללית. קריאת הביקורות המאושרות נשמרת. דפים ישנים שנותרו פתוחים לפני הפריסה עשויים להזדקק לרענון כדי לטעון את המסלול החדש.
6. לוודא ש-anon ו-authenticated אינם יכולים לקרוא למונה או לפונקציה, וש-INSERT ישיר לשתי הטבלאות נחסם. לבדוק הרשאות/API בסביבה הפעילה בלי להשאיר נתוני בדיקה.
7. להגדיר ולבדוק ניקוי מתוזמן של המונה; לבדוק אבטחה ולנטר שיעורי 429/503 לאחר ההפעלה.

אין להפעיל רק את ביטול INSERT לפני שהמסלול החדש עובד. אין לפרסם מצב server ללא הסודות והפונקציה, מפני שבמצב זה הטפסים ייכשלו באופן מבוקר.

## שחזור

אם יש תקלה, אפשר לפרוס תיקון למצב שרת בלי לפתוח שוב כתיבה ישירה. חזרה למסלול הישן דורשת החלטה מפורשת: להשיב את הרשאות INSERT המצומצמות בעמודות שאושרו בעבר ואז לפרוס מצב legacy. פעולה זו מסירה זמנית את הגבלת הקצב בצד השרת. אין לשנות את ארבע מגבלות התוכן או את סינון ביקורת הדמה. יש לשמור את הפונקציה והמונה עד שאין עוד פריסות שרת שמשתמשות בהם.

## ראיות ומגבלות הבדיקה

- 63 בדיקות רכיבים לשני המסלולים, לרבות 429, 503 ותקלה ברשת ללא ניסיון נפילה למסלול הישן.
- 28 בדיקות handler, לרבות הפרדת מקורות/טפסים, דחיית קלט, גודל גוף, timeout וכשל סגור. בדיקת המקביליות כאן משתמשת במאגר מדומה.
- SQL המיגרציה המדויק הורץ ב-PostgreSQL בזיכרון דרך PGlite 0.5.13, שהותקן בתיקיית TEMP לבדיקות בלבד: cooldown, חלון מתגלגל ומקרה גבול, איפוס, ביטול מכסה בהכנסה פסולה, ניקוי, הרשאות התפקידים וחסימת INSERT ישיר עברו.
- 20 פניות חופפות התקבלו פעם אחת ב-PGlite, אבל המנוע מסדר פניות בחיבור יחיד. בדיקת נעילות אמיתית בכמה חיבורים עדיין נדרשת לפני הפעלה.
- בדיקת SQL הזמנית דרך MCP של Supabase נקטעה בשגיאת requestState. אין תוצאת בדיקה מרוחקת מאומתת עבור מיגרציית הקצב; אין לטעון שהוחלה.
- סקריפטים: `check-form-flows.mjs`, `check-server-form-route.mjs`, `check-rate-sql-local.mjs`, `prepare-rate-sql-check.mjs`.

## הצעת גילוי בפרטיות בעת ההפעלה

עברית: בעת שליחת ביקורת או הצעה באתר, שרת האתר משתמש בכתובת המקור להגבלת קצב נגד שימוש לרעה. לצורך המונה נשמר במסד מזהה מחושב באמצעות סוד שרת, סוג הטופס וזמני שליחות, בלי לשמור את כתובת המקור הגלויה בשורת המונה. המונה אינו נשמר יחד עם תוכן הביקורת או ההצעה. יש לתאר את תקופת המחיקה בפועל לאחר הגדרת הניקוי המתוזמן. יומני התשתית כפופים למדיניות ספקי האירוח.
